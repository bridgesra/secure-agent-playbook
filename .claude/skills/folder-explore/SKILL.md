# Folder explore

Produce **[docs/repo-map.md](docs/repo-map.md)**: a compact index of every folder
and file in this repo, one line each, saying *what it is* and *when to open it*.

The map is the entry point for every later task — an agent reads the map, picks
the two or three files that matter, and reads only those. So the map must be
**cheap to read** and **accurate**. Optimise for an agent skimming it in one
pass, not for prose.

## When to do a full pass vs an incremental one

Read the marker comment on line 3 of `docs/repo-map.md`:

```
<!-- folder-explore: commit=<sha> generated=<YYYY-MM-DD> -->
```

- **No map file, no marker, or the user said "full"/"rebuild"** → full pass.
- **Otherwise** → incremental. Get the delta and touch only those files:
  ```bash
  git diff --name-status <sha> HEAD    # committed changes since last run
  git status --short                    # uncommitted changes
  ```
  Re-describe added and modified paths, delete lines for removed paths, and
  copy every other line through **verbatim**. Do not re-read unchanged files.

## Steps

1. **List the files.** This respects `.gitignore` and skips ignored noise:
   ```bash
   git ls-files --cached --others --exclude-standard
   ```
   Then drop anything matching `.claudeignore`, plus `.DS_Store`, lockfiles,
   and any directory with more than ~30 sibling files of the same type
   (describe that directory as a group, not file by file).

2. **Describe each file cheaply.** Never read a whole file just to describe it.
   - Markdown / text / code → `head -40` is almost always enough; use the H1,
     the first paragraph, and the section headings.
   - Structured config (`*.json`, `*.toml`, `*.yaml`) → read it; they are small.
   - HTML → `grep -o '<title>[^<]*' file.html` plus `head -30`.
   - Binary or opaque (`.docx`, `.pdf`, `.gdoc`, `.svg`, images) → describe from
     the filename and its folder context, and mark it `[binary]`. Do not try to
     extract text unless the user asks.
   - Batch reads with a single `head -40 a.md b.md c.md` where possible.

3. **Write one line per file**, ≤ 25 words, in this shape:
   ```
   - [name.md](path/to/name.md) — what it is; when you would open it.
   ```
   Say what is *inside* it, not what its name already says. `todo.md — a todo
   list` is a wasted line. `todo.md — THE checklist, week-by-week; tick boxes
   only here` earns its place.

4. **Write one blurb per folder**, one or two sentences: what the folder is for
   and what kind of question it answers.

5. **Flag staleness.** While traversing, note any cross-reference in a README or
   doc that points at a path that no longer exists. List these under
   `## Needs attention` in the map, and mention them to the user — do not fix
   them silently.

## Output format

Write exactly this structure to `docs/repo-map.md`:

```markdown
# Repo map

<!-- generated by the folder-explore skill; run it again after moving files -->
<!-- folder-explore: commit=<sha> generated=<YYYY-MM-DD> -->

<One sentence: what this repo is.>

## Start here
- <2-4 lines pointing at the files that answer the most common questions.>

## <path/to/folder>/
<Folder blurb.>

- [file.md](path/to/folder/file.md) — description.
- [sub/](path/to/folder/sub/) — see its own section below.

## Needs attention
- <stale cross-references, orphaned files, or gaps — omit the section if empty.>
```

Rules for the body:
- Folder sections in depth-first path order, so the map reads like a walk.
- Paths are relative to the repo root, always as markdown links.
- Dotfile config directories (`.claude/`, `.devcontainer/`, `.vscode/`) get one
  combined section at the end — one line each, no folder blurbs.
- Keep the whole map under ~200 lines. If it would exceed that, describe
  low-signal directories as a group instead of file by file.

## Finishing

Report to the user: how many folders and files are covered, whether it was a
full or incremental pass, and anything listed under `Needs attention`.
